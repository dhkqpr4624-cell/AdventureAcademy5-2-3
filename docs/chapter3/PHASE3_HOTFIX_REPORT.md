### 6) 공격 VFX 시작 시점
- 휘두르기(465 ms: windup 100 + swing 130 + settle 45 + return 190)가 **끝난 뒤** 시작하던 VFX를, 휘두르기와 **동시에** 시작하게 했습니다(`Promise.all`). 마무리 공격(finish)도 똑같이 바꿨습니다.
- 바꾸지 않은 것:
  - 타격(몬스터 피격 애니메이션, HIT SFX, 결과 메시지, 피해 처리)은 둘 다 끝난 뒤 1회만 일어납니다.
  - 정답 판정, 턴 전환, 무기별 VFX 선택, 몬스터 공격 VFX 타이밍
  - VFX 이미지는 새로 만들거나 바꾸지 않았습니다.
- 브라우저 실측. 기준은 휘두르기를 시작하는 「다음」 클릭이고, 시간은 VFX 시작 / 타격 메시지 순입니다.

| 무기 | 수정 전 | 수정 후 |
|---|---|---|
| 의병의 환도 | 498–960 ms / 2.4–3.4 s | **2–7 ms** / 1.4–2.1 s |
| 배움의 만년필 | 634–846 ms / 2.5–2.6 s | **1–5 ms** / 1.9–2.2 s |
| 나무 지팡이 | – | **3–4 ms** / 1.5–1.9 s |
| 기본(스킨 없음) | – | VFX 없음(기존과 같음) / 1.1–1.2 s |

  - 공격마다 VFX는 1회, 타격도 1회였습니다(두 번의 전투 승리, 피해 중복 없음).
  - 오답(빗나감)에는 VFX가 나오지 않습니다.
  - SwiftShader 환경이라 절대 시간은 실제 기기보다 깁니다.

### 7) 던전 최초 진입 로딩 최적화
- **실제 병목(조사 결과)**
  - 런타임에서 FBX를 parsing하지 않습니다. 오프라인에서 변환한 GSM2/GSL1 바이너리를 씁니다.
  - JS 처리 비용(Node 측정): 메시 parsing 13개 합계 약 8 ms, 레이아웃 계획 23–32 ms, 맵 생성 1 ms 미만. 병목이 아닙니다.
  - 병목 ①: **매 진입마다 건물·도로 에셋 19개 요청(합계 8.1 MB)과 parsing·decode를 처음부터 다시** 했습니다. Pages 캐시가 만료된 뒤에는 다시 내려받습니다.
  - 병목 ②: 첫 프레임에서 GPU 업로드와 shader compile이 길게 걸립니다.
  - 병목 ③: **2층 진입 순간 스토리 일러스트 약 15 MB를 내려받기 시작해** 건물 모델과 대역폭을 다퉜습니다.
- **적용한 것**
  - 파싱한 geometry와 texture를 세션 동안 공유 캐시에 보관합니다(재진입, 층 전환, 재도전 시 다시 요청·parsing하지 않음).
    - 화면을 벗어날 때는 해당 renderer의 GPU 사본만 해제합니다.
    - 텍스처는 `Image.decode()`로 메인 스레드 밖에서 decode합니다.
  - 베이스캠프에서 idle 시간에 하나씩 사전 로딩합니다(진입 2.5초 후 시작, 베이스캠프를 벗어나면 중단).
    - 순서: 던전 화면 코드 → 경성 건물·도로 → 개방된 층 몬스터 이미지 → 장착 무기 VFX → 진행 중인 층의 스토리 일러스트(다운로드만)
    - 타이틀과 인트로에서는 불러오지 않습니다.
  - 층 일러스트 decode는 거리 준비가 끝난 뒤로 미룹니다.
  - 모델이 아직 없을 때만 로딩 화면을 씁니다. 기존 인트로 로딩 화면과 같은 스타일로 「던전으로 들어가는 중입니다.」를 보여 줍니다. 빈 3D 거리를 먼저 보여 주지 않습니다.
    - 모델이 준비되면 기존 3.2초 층 제목 전환이 시작됩니다.
    - 이미 캐시에 있으면 로딩 화면은 **나오지 않습니다**. 인위적으로 늦추지 않습니다.
    - 네트워크가 극히 느리면 20초 안전장치가 있습니다.
  - 화면을 벗어날 때 `renderer.forceContextLoss()`로 WebGL context를 바로 해제합니다.
- **시도했다가 되돌린 것**: `compileAsync`와 `initTexture` 사전 준비
  - 이 환경에서 효과는 확인할 수 없었고, 로딩 화면을 약 2.5초 더 붙잡는 손해는 확인됐습니다. 그래서 제거했습니다.
- 바꾸지 않은 것: 건물 크기, 도로 폭, 방 간격, 이동 속도, 카메라, 에셋 디자인, 텍스처 품질, 랜덤 구조, 이벤트 연결
- **측정 결과**
  - 측정 조건:
    - Pages와 같은 캐시 헤더(`max-age=600`, ETag)를 주는 로컬 서버를 썼습니다.
    - 던전 진입부터 20 Mbps로 제한했습니다.
    - 480×270, SwiftShader(소프트웨어 렌더링)
  - 「거리 완성」은 페이지 프레임 타임스탬프 기준으로, 프레임당 draw call이 40개 이상인 첫 프레임까지의 시간입니다(정상 상태 55–62개).
  - 표의 「사전 로딩 후」는 베이스캠프에서 6초 머문 뒤 진입한 경우, 「사전 로딩 전」은 1.2초 만에 바로 진입한 경우입니다.

| 진입 | 수정 전: 거리 완성 / 요청·용량 / 최장 long task | 수정 후 (사전 로딩 후) | 수정 후 (사전 로딩 전) |
|---|---|---|---|
| 최초 1층 (cold) | **11.6 s** / 19건 8.1 MB / 4.7 s | **1.5 s** / 0건 / 0.5 s | 12.0 s / 19건 8.1 MB / 4.3 s (빈 거리 대신 로딩 화면) |
| 두 번째 1층 | 1.4 s / 19건(재검증) / 0.4 s | 1.2 s / **0건** / 0.5 s | 1.2 s / 0건 / 0.5 s |
| 1층 귀환 후 2층 | **14.3 s** / 15건 / 4.4 s | **1.1 s** / 0건 / 0.4 s | 1.2 s / 0건 / 0.4 s |
| 1층 반복 3회 | 1.3 / 1.4 / **6.8** s (5.6 s long task 1회) | 1.0–1.4 s | 1.0–1.2 s |

  - 중복 parsing: 수정 전에는 진입마다 메시 13개와 텍스처 6개를 다시 처리했습니다. 수정 후에는 세션당 1회입니다.
  - 메모리(JS heap, GC 후)
    - 수정 전: 베이스캠프 4.2 MB → 진입 6회 후 9.1 MB
    - 수정 후: 사전 로딩 뒤 13.7 MB → 진입 6회 후 16.5 MB
    - 늘어난 약 9.5 MB는 캐시된 모델이고, 진입할 때마다 늘어나지 않습니다(회당 약 0.5 MB 증가로 수정 전과 같음).
  - GPU 객체: 화면 안의 buffer와 program 수가 매번 같은 범위로, 계속 쌓이지 않습니다.
  - 사망 후 즉시 재도전: 같은 scene을 다시 쓰고 에셋을 다시 불러오지 않습니다(수정 전후 동일). 시간은 따로 재지 않았습니다.
- **한계**
  - **실제 학교 노트북이나 크롬북에서는 측정하지 못했습니다.**
  - SwiftShader에서는 GPU 작업이 CPU에서 돌기 때문에 프레임 시간의 절대값은 실제 기기보다 훨씬 깁니다.
  - 사전 로딩 없이 첫 진입하면 8.1 MB 다운로드 시간은 그대로입니다. 네트워크 한계입니다.
  - 캐시를 쓰는 경우, 첫 프레임에 거리 전체를 한 번에 올리기 때문에 진입 직후 화면 전환이 한 번 길게 멈출 수 있습니다. SwiftShader에서는 1–2초였고 실제 GPU에서는 훨씬 짧을 것으로 예상합니다. 수정 전에는 같은 비용이 진입 후 건물이 하나씩 나타나면서 생겼습니다.

### 8) 스토리 전투 방 재방문
- 원인: 1층 짐수레 방과 2층 학교 방의 「방 완료」를 영구 스토리 플래그로 정해서, 스토리를 마친 뒤의 새 도전에서는 빈 방이 됐습니다.
- 수정: 영구 스토리 상태(플래그)와 현재 도전의 전투 완료 상태(room progress)를 분리했습니다.

| 상황 | 동작 |
|---|---|
| 최초 방문 | 스토리 → 필수 전투 → 승리 후 대화 (기존과 같음) |
| 같은 도전 중 재방문 | 완료된 방. 몬스터가 다시 나오지 않습니다 |
| 새 도전 (재입장 또는 다시 도전하기) | 스토리와 일러스트 없이 **일반 전투**(그 층 일반 몬스터, 2문제, 그 도전의 랜덤 출제). 스토리 기록, 보상, 업적은 바뀌지 않습니다 |

- 순수 대화 방(시작 방, 스토리 방 3개)과 마지막 방에는 몬스터를 추가하지 않았습니다(자동 검사 10개 시드 × 2층).
- 브라우저 확인:
  - 짐수레 방이 새 도전에서 전투가 됐습니다.
  - 같은 도전 안에서 왕복하면 전투가 0회였습니다.
  - 사망 후 다시 도전하면 다시 전투가 됐습니다.

### 11) 던전 BGM
- `unit3-dungeon` 트랙을 추가했고, 1층과 2층이 함께 씁니다. 층별 지정은 `App`의 `UNIT3_DUNGEON_FLOORS[floor].bgm`에서 합니다.
- **재생 규칙**
  - 던전에 들어가면 재생을 시작합니다. 베이스캠프 BGM은 1초 동안 줄어들고, 던전 BGM은 1.8초 동안 커집니다.
  - 탐험, 일반·정예 전투, 스토리, 일러스트, 다시 도전하기 내내 **같은 요소가 계속 재생**됩니다. 실측 결과: `play()` 호출 1회, seek는 loop 시작점 1.4초로만 있었고 0으로 간 적이 없습니다.
  - 베이스캠프로 돌아가면 던전 BGM이 1초 동안 줄어들고 베이스캠프 BGM으로 바뀝니다.
  - 타이틀로 가면 모두 멈춥니다.
  - 이어하기와 새로고침 후 이어하기에서는 베이스캠프 BGM만 재생됩니다.
  - 작전본부와 베이스캠프 BGM, 워프 SFX(`chapter3ProceduralSfx.ts`)는 수정하지 않았습니다.
- **음량** (ffmpeg `ebur128` LUFS와 true peak 측정). 기존 방식처럼 곡별 trim으로 −25.5 LUFS 기준에 맞추고, 원본 WAV는 그대로 둡니다.

| 곡 | 원본 I / peak | trim | 실제 volume (0.42×trim) | 출력 I / peak (계산) |
|---|---|---|---|---|
| INTRO_ADVENTUREACADEMY | −12.2 LUFS / −0.1 dBFS | 0.216 | 0.0907 | −33.0 LUFS / −21.0 dBFS |
| BASECAMP (unit3-basecamp) | −19.0 / −0.8 | 0.473 | 0.1987 | −33.0 / −14.8 |
| **던전 BGM** | −15.8 / −0.9 | **0.327** | **0.1373** | **−33.0 / −18.1** |

  - 브라우저에서 analyser로 측정한 실제 출력:
    - 베이스캠프: RMS 평균 −40.0, p95 −32.9, peak −17.8 dBFS
    - 던전: RMS 평균 −38.1, p95 −32.3, peak −23.5 dBFS
    - 두 곡의 차이는 2 dB 이내이고 clipping은 없었습니다.
  - 전투 SFX와 대사 효과음은 바꾸지 않았습니다. BGM이 베이스캠프와 같은 체감 음량이라 SFX가 묻히지 않습니다.
  - 사용자 볼륨 설정은 2단원과 3단원 모두 **존재하지 않습니다.** 모든 BGM은 같은 `effectiveBgmVolume` 경로를 쓰므로, 나중에 볼륨 설정을 추가하면 함께 적용됩니다.
- **Loop**
  - 원본 앞부분에 디지털 무음 **1.43초**가 있습니다. 끝부분은 리버브 꼬리가 119.6초까지 이어집니다(115초 −36 dB, 117초 −56 dB).
  - loop 구간: **1.40초 → 118.20초**. 꼬리는 −60 dBFS 아래로 떨어질 때까지 남겼습니다.
  - 파일은 바꾸지 않고 재생 위치만 조정합니다.
  - 첫 재생도 1.40초부터 시작합니다.

  - 기존 세이브 10종 정상 로드: 미수락, 수락, 짐수레 완료, 이벤트 완료, 층 완료(복귀 대사), 완료, 환도 장착, 2층 수락·일부·마지막
  - 2층 스토리 방 순서 테스트(학교 전투 완료 세이브, 순서 3→2): 이후 대화 1회, 각 스토리 1회, 시작 스토리 재생 없음, 콘솔 오류 0
    - 새 도전에서 학교 방은 스토리 없이 아부쟁이 친일파와 2문제 일반 전투로 나왔습니다.
    - 첫 실행은 HP가 부족해 사망했습니다(학교 방 전투가 추가됐고, 테스트 도우미가 한 문항을 오답 처리). 테스트에 「다시 도전하기」 처리를 넣고 다시 실행해 통과했습니다.

## 5. 임시 처리 · 미완성 · 지시와 다른 부분
- **임시**: 2층 문제는 여전히 임시 풀(1층과 같은 문항)입니다. 집계는 층별로 분리되어 있습니다.
- 실제 문제로 바꾸면, 새 풀에 없는 임시 문항 기록은 자동으로 세지 않습니다. 그래서 진행도가 줄어들 수 있습니다(의도된 동작).
- 레거시 `floorBestCorrect` 최고치는 풀을 바꿔도 남아 있는 하한값으로 계속 인정됩니다.
- **지시와 다른 부분**
  - 업적 메달은 전용 아이콘 이미지가 없어 기존 ★ 메달을 그대로 씁니다.
  - 스토리 전투 방의 새 도전 몬스터: 원래 그 방의 몬스터(1층 먹물 든 을사늑약 문서, 2층 아부쟁이 친일파)를 씁니다. 둘 다 그 층의 일반 몬스터입니다. 일반 방처럼 두 종류 중 무작위로 고르지는 않습니다.
  - 「처음 화면」 버튼은 업적 창과 층 선택 창이 열려 있는 동안 숨깁니다. 작은 화면에서 × 버튼을 가렸기 때문입니다.
  - 셰이더 사전 컴파일은 위 7번 이유로 넣지 않았습니다.
- **기존부터 있던 동작(수정하지 않음)**: 2단원과 같이 다시 도전하면 보물상자 방도 초기화됩니다. 죽고 다시 도전하면 상자 골드를 다시 얻을 수 있습니다.
